Intel DCI on Z390 — debugging your own machine (sort of)

intel dci jtag firmware z390 hardware

hey. this is my second entry, and it's essentially a continuation of my wanderings through the world of hardware hacking. today we're touching on a genuinely interesting piece of Intel technology: DCI — Direct Connect Interface.

the short pitch: DCI lets you debug hardware directly. not through the OS, not through a hypervisor, not through software abstractions — directly. compared to this, USB/serial debugging feels like sending letters by postal mail.

what DCI gives you in theory:

per-thread visibility
observe every thread and core, even on a hung or locked system
register / memory access
direct read/write to CPU registers and physical memory
processor trace
full execution trace — who touched what register, when, in what order
halt & resume
stop the machine mid-execution and look around. like GDB but at ring -∞

think of it as a VM debugger, except the "VM" is your actual physical machine. the control software is basically Intel's proprietary WinDbg. and yes — this only exists from Skylake onwards, so my H61 from log_000 is sitting this one out entirely. (sorry old friend.)

hardware this time

for once, i'm testing on my main machine. coffee lake = DCI capable. no excuses.

cpuIntel Core i7-9700K (Coffee Lake)
boardASUS PRIME Z390-A
ramG.Skill 32 GB @ 3600 MHz
psu1000W (finally, a real PSU)

step 1 — bios dump and hidden settings

tool: amibcp + intel fit

as always: dump the firmware first. i can't stress this enough. i used a programmer for this, but if you don't have one nearby, Intel FPT, Chipsec, or flashrom will get the job done. i usually default to FPT — it's familiar.

with the dump in hand, i went digging. board vendors typically don't remove DCI-related settings — they just hide them from the UI. which means they're still there, waiting. i started with AMIBCP for analysis, same as with the older boards. found versions 4.55 and 5.02 online, but both choked on this dump with an "exceeded row count" error.

workaround: downgrade the firmware from version 2101 (my latest) to 1401. that made AMIBCP happy and the file opened. inside: the DCI fields — USB DCI support, DCI DbC, and others.

after editing and saving, the obvious question: how do you flash this back? ran Chipsec and flashrom — both confirmed the flash is write-protected. so, programmer time.

new problem: modern ASUS boards typically have the BIOS chip soldered directly to the PCB instead of sitting in a socket. no clip, no easy extraction. but there's an alternative: SPI flash header.

the board exposes the flash programming pins directly on the PCB. no desoldering required — connect the programmer to the header, flash. you can order a proper connector, but i made mine from pins salvaged from an old case. works fine.

in my setup it was necessary to supply 3.3V from the programmer rather than using standby voltage from the board. pay attention to this.
voltage experiments (don't try this at home)
since i was already there, i ran some experiments so you don't have to. flashed with standby voltage only — fine. flashed with 3.3V only — fine. flashed with both simultaneously — fine. swapped wires around — fine. the flash chip is surprisingly hard to kill. but seriously, don't do this. it's not worth the risk and i got lucky.

flashing started fine. then the board bricked. no POST, no response, nothing. tried reflashing the modified image several different ways — no luck. turns out AMIBCP doesn't correctly write its changes back into the binary. it reads fine, it edits fine, it just silently corrupts the output. great tool.

pivoted to Intel FIT (Flash Image Tool) — a utility for configuring firmware images and the ME region directly.

Intel ME (Management Engine) is an autonomous low-power subsystem embedded in virtually all Intel chipsets since 2008. it runs independently of the main CPU, BIOS, and OS. FIT lets you configure it — including enabling or disabling various hardware debug interfaces.

in FIT: disabled all write protections, enabled DCI, enabled the relevant debug ports. flashed. board came back up.

step 2 — second machine and the cable

interface: usb 3.0 dbc

DCI requires two machines: the target (the one being debugged) and the host (the one running the debugger). the proper Intel hardware for this — the SVT CCA — costs more than my entire setup combined, so we're using USB 3.0 with the DbC (Debug Class) protocol instead.

cable: bought a standard USB 3.0 cable for $3. before using it, stripped the insulation and cut the red wire (VBUS). this makes sure the two machines aren't sharing power rails. probably unnecessary, but it's a two-second precaution.

[~] connected both machines. no response. something is blocking it.

step 3 — nvram editing

tool: scewin

since we couldn't expose the DCI settings through the UEFI UI, the next option is editing NVRAM directly. NVRAM holds the UEFI variable store — settings that persist across reboots until you pull the CMOS battery.

you can dump NVRAM with IFR Extractor and edit values manually through GRUB2, but the easier path on Windows is SCEWin: dumps NVRAM to a readable file, you edit the values directly, then write it back.

after applying the NVRAM edits and rebooting, the system came up on the third attempt. three reboots on first apply = the changes took effect, the firmware is doing its initialization dance.

[+] system booted after 3 attempts. NVRAM changes applied.

then: a new USB device appeared on the target machine. a "Synaptics USB controller" — spelled incorrectly, as "controler". (an Easter egg from Intel, or just a typo that shipped to production and nobody cared. either way, charming.) on the host side: an unknown USB device.

step 4 — debugger software

tool: intel system studio 2020

you can't just talk to DCI with a raw terminal. you need Intel System Studio, which in 2026 has been absorbed into OneAPI and become genuinely unpleasant to use. found a 2020 standalone build floating around — it works.

OpenBMC is theoretically an option here too, but without Intel's proprietary drivers, you're not going to get far. System Studio it is.

after installing and connecting: i got in. partial connection to the target machine.

[+] DCI connection established.
[-] CPU link: not available. PCI lines only.

what we actually have

DMA access
available — read/write physical memory via PCI
JTAG / halt
not available — no CPU link
PCIe config registers
available — pre-initialization access to all devices
processor trace
not available — requires full CPU link
GPIO / clock config
available
SPI flash r/w
available

the deep dive — and the wall

no CPU link was frustrating. spent a significant chunk of time comparing results against other platforms and boards, reviewing BIOS settings, going through every port on the machine. found one USB port that responded more strongly than the others — when you lose contact with it, the machine reboots. that's a good sign. but still no processor link.

bought a dedicated DCI cable from a Chinese vendor for $30, advertised as "guaranteed to work" etc. identical result. cables aren't the problem.

found a boardview and schematic for the Z390-A. probed the relevant contacts with a multimeter — signal is present. traced the DCI lines through the schematic looking for anything abnormal.

then found it.

on the schematic: a set of resistors with the annotation "place these resistors to enable DCI". they are not populated on the production board. ASUS cut the DCI line at the PCB level — the CPU literally cannot enter debug mode without these components physically present. some boards don't have this, depends on the vendor and revision. this one does.

[-] CPU debug link physically severed by unpopulated resistors. full DCI requires board-level rework.

what we kept — pci_dma

capability: dma access over pci

no processor trace. no halt. no per-core visibility. but we kept PCI_DMA — and that's not nothing.

what PCI DMA access means in practice:

— direct memory read/write bypassing IOMMU protection
— access to PCIe device config registers before OS initialization
— GPIO, clock generator, and power controller configuration
— SPI flash read/write access
— appears in Windows as a Synaptics device — nothing suspicious in device manager

DMA (Direct Memory Access) allows a device to read and write system memory without CPU involvement. IOMMU is the hardware mechanism that normally restricts which memory regions a device can reach. bypassing it means you can read/write arbitrary physical memory from the PCI bus.

the appearance as a Synaptics device is significant — from a software perspective, nothing unusual is inserted into the PCIe slot. the access vector is essentially invisible to anything looking at the standard device tree.

use cases are wide. i'll leave the obvious ones as an exercise. one reminder: this is research territory. everything here is your own responsibility. i'm not pushing anything — just documenting what the hardware actually does when you push it.

and for the record: this doesn't replace a proper DMA card, and writing production tooling on top of this without Intel's driver stack is a significant undertaking.
